# Intent Envelope, version 0.1

An agent that does something helpful nobody asked for has failed, even if nothing was
breached. The intent envelope is the artifact that makes "what was this agent for?" a
question a machine can answer at the moment a tool call is made.

This document specifies the envelope. It does not specify how to enforce it, because
enforcement belongs to whatever sits between your agent and its tools.

## 1. What an envelope is

An envelope is a JSON document, written before the agent runs, by the people who own
the workflow. It is reviewed like an access policy and versioned like code. It states:

- **Purpose**: what this agent is for, in terms a reviewer can approve or reject.
- **Principal**: the agent's own identity, and whose authority it borrows.
- **Tools**: the only tools it may call, with constraints on their arguments.
- **Data**: what it may reach.
- **Recipients**: who it may send anything to. Absent means nobody.
- **Limits**: the budget a run may consume before it is stopped.
- **Escalation**: which actions pause for a named human, and what happens if nobody answers.
- **Expiry**: when the envelope stops being valid.

The schema is at `schema/intent-envelope-0.1.json`, published at
`https://securedai.org/schemas/intent-envelope/0.1.json`.

## 2. What an envelope is not

It is not a prompt. Text inside the model's context can be argued with by anything else
in that context, including a sentence hidden in a document the agent was asked to read.
An envelope is checked in code, by something the model cannot talk to.

It is not a judgement of whether the goal was wise. It limits the damage when
understanding fails. That is the whole claim.

## 3. Evaluating a call against an envelope

An enforcement point MUST evaluate every proposed tool call and return exactly one of
`allow`, `deny` or `escalate`.

1. If the envelope has an `expires` in the past, the result is `deny`.
2. If the tool appears in `tools.deny`, the result is `deny`. Deny always wins, and a
   later change that widens `tools.allow` MUST NOT override it.
3. If the tool does not appear in `tools.allow`, the result is `deny`.
4. If the call's arguments violate that grant's `constraints`, the result is `deny`.
5. If the call would read data outside `data.allow`, or matching `data.deny`, the result
   is `deny`.
6. If the call would contact anyone outside `recipients.allow`, or exceed
   `recipients.max_per_run`, the result is `deny`. An absent `recipients` means the agent
   may contact nobody.
7. If any `limits` value would be exceeded by this call, the result is `deny`.
8. If any `escalate` condition matches, the result is `escalate`.
9. Otherwise the result is `allow`.

Deny is evaluated before escalate so that a forbidden action is never presented to a
human as an approvable one.

## 4. Escalation

An `escalate` entry names a condition and a human. The human MUST be a named person or
a rota, never an unattended mailbox.

`on_no_response` states what happens when an escalation is never answered. A conforming
implementation MUST support `deny`. It MAY support `allow`, and if it does, it SHOULD
make that choice visible in the record of the run, because an unattended approval that
defaults to allow is not a control.

## 5. Recording

Every evaluation SHOULD produce one record containing: the envelope `id` and `revision`,
the agent identity, the principal, the tool and its target, the result, the rule that
decided it, and the cost attributed to the call. The envelope is the only place that
knows all of these at once, which is why the record is written where the decision is made
rather than assembled afterwards from logs.

## 6. Conformance

An implementation conforms to this version when, for each file in `conformance/valid`,
it accepts the envelope, and for each file in `conformance/invalid`, it rejects it with
an error naming the offending field.

## 7. Open questions for 0.2

These are deliberately unspecified in 0.1, and we would rather hear from implementers
than guess:

- A standard expression syntax for `escalate.when`. Deployments differ enough that 0.1
  leaves it to the enforcement point.
- Whether `data` addressing should be normative rather than deployment-defined.
- Delegation: how an envelope narrows when one agent calls another.
- Signing, so an enforcement point can verify an envelope was approved by a named reviewer.

## 8. Keywords

MUST, MUST NOT, SHOULD and MAY are used as described in RFC 2119.
