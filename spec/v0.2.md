# Intent Envelope, version 0.2 (draft)

An agent that does something helpful nobody asked for has failed, even if nothing was
breached. The intent envelope is the artifact that makes "what was this agent for?" a
question a machine can answer at the moment a tool call is made.

This document specifies the envelope. It does not specify how to enforce it, because
enforcement belongs to whatever sits between your agent and its tools.

**Status: draft.** 0.2 adds four optional blocks and one procedure to
[version 0.1](v0.1.md), and changes nothing 0.1 says. Every 0.1 envelope is still valid
and decides exactly as it did, because each new rule reads a block a 0.1 envelope cannot
carry. An envelope opts in by declaring `"intent_envelope": "0.2"`. Section 9 lists what
changed and the incidents that asked for each change.

## 1. What an envelope is

An envelope is a JSON document, written before the agent runs, by the people who own
the workflow. It is reviewed like an access policy and versioned like code. It states:

- **Purpose**: what this agent is for, in terms a reviewer can approve or reject.
- **Principal**: the agent's own identity, and whose authority it borrows.
- **Tools**: the only tools it may call, with constraints on their arguments.
- **Data**: what it may reach.
- **Recipients**: who it may send anything to. Absent means nobody.
- **Limits**: the budget a run may consume before it is stopped.
- **Escalation**: which actions pause for a named human, and what happens if nobody answers.
- **Expiry**: when the envelope stops being valid.
- **Egress** (0.2): which hosts its tools may reach over the network.
- **Credentials** (0.2): what a credential it uses must be bound to, and how long it may live.
- **Processors** (0.2, under `data`): which inference providers and subprocessors data may reach.
- **Amendment** (0.2): who may change the envelope, and which tools change it.
- **Components** (0.2): whether a server, skill or plugin must declare what it brings.

The schema is at `schema/intent-envelope-0.2.json`, published at
`https://securedai.org/schemas/intent-envelope/0.2.json`. The 0.1 schema stays where it is.

## 2. What an envelope is not

It is not a prompt. Text inside the model's context can be argued with by anything else
in that context, including a sentence hidden in a document the agent was asked to read.
An envelope is checked in code, by something the model cannot talk to.

It is not a judgement of whether the goal was wise. It limits the damage when
understanding fails. That is the whole claim.

It is not something the agent declares about itself. An envelope is authored by the
people who own the workflow, before the run, and reviewed like any other access policy.
That direction is the whole reason it works, and section 2.1 states what follows from it.

### 2.1 What the envelope assumes

An envelope is a constraint people wrote. A model that has learned it is useful to
misrepresent its own reasoning can describe its intentions convincingly and wrongly, so
an envelope the agent authored would inherit that problem completely. Three requirements
follow.

1. An envelope an agent can write is not a control. If an agent can draft its own, or
   widen an existing one, the system is asking permission from itself. Implementations
   MUST treat creating or modifying an envelope as a privileged operation that the agent
   the envelope governs cannot perform.

2. What the agent supplies at call time remains the agent's own claim. The envelope is
   trustworthy; the arguments and targets of a particular tool call are not, because they
   come from the thing being constrained. An enforcement point MUST evaluate constraints
   against independently derived facts, such as what a record actually contains or who a
   recipient actually is, rather than against the agent's description of the call.

3. The envelope is necessary and not sufficient. It states what is permitted. Whether a
   given call falls inside it is decided in code, outside the model, by the evaluation in
   section 3. An envelope with nothing enforcing it is a document.

These requirements hold whatever caused the agent to propose the action. An envelope does
not distinguish between a model manipulated through its context and a model pursuing an
objective shaped during training, and it does not need to: both arrive as a tool call that
either falls inside the declared intent or does not.

## 3. Evaluating a call against an envelope

An enforcement point MUST evaluate every proposed tool call and return exactly one of
`allow`, `deny` or `escalate`, in this order. Steps marked 0.2 apply only when the
envelope carries the block they read.

1. If the envelope has an `expires` in the past, the result is `deny` (rule `expires`).
2. If the tool appears in `tools.deny`, the result is `deny` (`tools.deny`). Deny always
   wins, and a later change that widens `tools.allow` MUST NOT override it.
3. (0.2) If the tool appears in `amendment.protected_tools`, the result is `deny`
   (`amendment`), whatever `tools.allow` says. These are the tools that change envelopes,
   policies or controls, and section 2.1 requirement 1 forbids the governed agent from
   using them. It is checked before `tools.allow` so that the record names the reason an
   operator needs to know: the agent tried to change its own envelope.
4. If the tool does not appear in `tools.allow`, the result is `deny` (`tools.allow`).
5. If the call's arguments violate that grant's `constraints`, the result is `deny`
   (`tools.constraints`).
6. (0.2) If the envelope has a `credentials` block, the call's credential facts MUST
   establish that the credential is bound to this run (and, with `bind: "task"`, this
   task), that it has an expiry no later than the envelope's, and, with
   `max_lifetime_seconds`, that it was not issued for longer. Missing facts, a different
   run or task, a later expiry or a longer lifetime are each `deny` (`credentials`).
7. If the call would read data outside `data.allow`, or matching `data.deny`, the result
   is `deny` (`data`).
8. (0.2) If the envelope has `data.processors` and the call would send data to a processor
   not on it, the result is `deny` (`data.processors`). Present and empty means none.
9. (0.2) If the envelope has an `egress` block and the call would reach a host matching
   `egress.deny`, or, with `egress.allow` present, a host matching nothing on it, the
   result is `deny` (`egress`). Deny is checked first.
10. If the call would contact anyone outside `recipients.allow`, or exceed
    `recipients.max_per_run`, the result is `deny` (`recipients`). An absent `recipients`
    means the agent may contact nobody.
11. If any `limits` value would be exceeded by this call, the result is `deny` (`limits`).
12. If any `escalate` condition matches, the result is `escalate` (`escalate`).
13. Otherwise the result is `allow` (`allow`).

Deny is evaluated before escalate so that a forbidden action is never presented to a
human as an approvable one.

The facts the 0.2 steps read, the credential, the processors and the hosts, are subject
to section 2.1 requirement 2 like every other fact: an enforcement point MUST establish
them itself, from the credential's issuer, the routing configuration and the resolved
destination, rather than from the agent's description of the call.

### 3.1 Host patterns (0.2)

A pattern in `egress.allow` or `egress.deny` is one of: an exact host name or IP address;
a host name with a leading `.` or `*.`, which matches any subdomain and never the bare
domain itself; or an IPv4 range in CIDR notation. Matching is case-insensitive and ignores
one trailing dot. `.example.com` matches `api.example.com` and not `example.com` or
`badexample.com`.

## 4. Escalation

An `escalate` entry names a condition and a human. The human MUST be a named person or
a rota, never an unattended mailbox.

`on_no_response` states what happens when an escalation is never answered. A conforming
implementation MUST support `deny`. It MAY support `allow`, and if it does, it SHOULD
make that choice visible in the record of the run, because an unattended approval that
defaults to allow is not a control.

## 5. Recording

Every evaluation SHOULD produce one record containing: the envelope `id` and `revision`,
the agent identity, the principal, the tool and its target, the result, the rule that
decided it, and the cost attributed to the call. The envelope is the only place that
knows all of these at once, which is why the record is written where the decision is made
rather than assembled afterwards from logs.

## 6. Changing an envelope (0.2)

0.1 required that changing an envelope be privileged and beyond the governed agent, and
left how to the deployment. 0.2 makes it checkable.

An envelope MAY carry `amendment.approvers`: named people, each with an Ed25519 public
key. A new revision of that envelope is accepted only when all of these hold:

1. It has the same `id`, and a higher `revision`.
2. It carries a signature, by one of the approvers named in the revision **it replaces**,
   over its canonical form. An approver named only in the new revision cannot approve it;
   otherwise a change could name its own approver.
3. The signature verifies.

The canonical form is the envelope as JSON with object keys sorted, no insignificant
whitespace, and numbers with an integer value written without a decimal point (`2.0` is
`2`), so that every implementation signs and verifies the same bytes.

An envelope with no `amendment.approvers` cannot be changed this way at all. It is changed
through whatever review the policy repository has, as in 0.1.

An implementation SHOULD list every way the new revision widens the old, so the approver
sees what they are granting, and SHOULD produce a record of every proposal, accepted or
refused, with its reasons. A refused proposal is evidence that something tried to widen
an envelope, and is worth keeping for exactly that reason.

## 7. Admitting a component (0.2)

A component is an MCP server, a skill or a plugin that brings tools into an agent's
toolset. It MAY publish a manifest: its `name`, the `tools` it exposes, the `egress` hosts
it reaches, the `data` it reads and the `processors` it sends data to.

A component is admitted only when everything its manifest declares is inside the envelope:
every tool on `tools.allow` and on neither `tools.deny` nor `amendment.protected_tools`;
every host permitted by `egress` (and, when the envelope has no `egress` block, a
component that declares any host is refused, because its reach cannot be checked); every
data target within `data`; every processor on `data.processors`.

With `components.require_manifest: true`, an enforcement point MUST refuse to govern a
component that has no manifest. Once a component is admitted, a tool it exposes that its
manifest did not declare MUST be refused (rule `components`) even if the envelope grants
it: the envelope granted the tool, but this component was not admitted to provide it.

## 8. Conformance

An implementation conforms to this version when all five hold.

1. For each file in `conformance/valid`, it accepts the envelope.
2. For each file in `conformance/invalid`, it rejects it with an error naming the
   offending field.
3. For each file in `conformance/decisions`, given that envelope, that proposed call and
   that run state, it returns the expected result AND names the same rule.
4. For each file in `conformance/amendments`, it accepts or refuses the proposal as
   expected, with the expected reason, and lists the expected widening.
5. For each file in `conformance/components`, it admits or refuses the manifest as
   expected, with the expected reasons.

The third is the one that matters at runtime. Accepting a well-formed envelope and then
deciding calls differently from this specification is not a partial implementation, it is
a different control with the same name on it.

Naming the rule is part of conformance rather than a convenience. Section 5 requires the
record to carry the rule that decided, and an operator reading a refusal acts on that
field. An implementation that returns `deny` for the wrong reason has told them
something false.

Two rules in section 3 depend on things this version leaves deployment-defined: `data`
addressing, and the expression syntax in `escalate.when`. An implementation supplies
those two matchers. Everything else in section 3 is decided by this specification.

## 9. What 0.2 changes, and why

| Addition | Asked for by |
| --- | --- |
| `egress` and host patterns | A fetch tool pointed at the instance metadata service (Bedrock AgentCore); agents that left containment through DNS and a third-party fetcher (Trajectory Labs); a sentence in a skill asking for data to be sent out (OX Security) |
| `credentials` | Credentials handed to an agent and used after the run that needed them (Google and Mandiant); one vendor key that reached 5,000 machines (Cursor) |
| `data.processors` | Chat transcripts at a fourth party nobody chose (Notion and Fireworks); a no-retention flag enforced only by the provider (the Dragos canary test) |
| `amendment` | An application that assigned itself Global Administrator (NCSC and Microsoft); a design where an agent writes the control and something else must decide it runs (OpenAI and Cisco, Shirudo) |
| `components` | Poisoned instructions in 22 percent of flagged MCP servers (OX Security) |

The briefings are at https://securedai.org/community.

## 10. Open questions for 0.3

These remain unspecified, and we would rather hear from implementers than guess:

- A standard expression syntax for `escalate.when`. Deployments differ enough that 0.1
  leaves it to the enforcement point.
- Whether `data` addressing should be normative rather than deployment-defined.
- Delegation: how an envelope narrows when one agent calls another.
- Signing the envelope itself, beyond the amendment signature in section 6, so an
  enforcement point can verify the revision it loads.
- IPv6 ranges in host patterns.

## 11. Keywords

MUST, MUST NOT, SHOULD and MAY are used as described in RFC 2119.
