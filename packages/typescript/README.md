# intent-envelope

Declare what an AI agent is for, and enforce it in code at every tool call.

An intent envelope is a short, human-authored document that says what one agent is
allowed to do: which tools, which data, which recipients, what limits, and who to ask
when something falls outside those bounds. This package reads that document and decides
each tool call against it, before the call runs.

The envelope is written by a person, not inferred from an agent's behaviour and not
generated by a model. That is the point. An agent cannot be trusted to describe its own
purpose, so the description has to come from outside it.

Implements [Intent Envelope 0.1](../../spec/v0.1.md). Apache-2.0.

## Install

```sh
npm install intent-envelope
```

Requires Node 22.18 or newer. No runtime dependencies: the schema validator here
implements the fourteen JSON Schema keywords the envelope schema uses rather than
pulling in a general one, because a security package whose install drags in a
dependency tree is a worse security package.

## Use

```ts
import { EnforcementPoint, Refused, validate } from 'intent-envelope';

const envelope = {
  intent_envelope: '0.1',
  id: 'invoice-reconciler',
  revision: 3,
  purpose: 'Reconcile this month’s supplier invoices against the ledger and email a summary to the AP team.',
  principal: { agent_identity: 'invoice-reconciler', on_behalf_of: 'finance.ap_team' },
  tools: {
    allow: [
      { name: 'read_invoice', constraints: { period: 'current_month' } },
      { name: 'send_email', constraints: { template: 'mismatch_summary' } },
    ],
    deny: ['issue_payment', 'http_request'],
  },
  recipients: { allow: ['ap-team@example.com'], max_per_run: 3 },
  limits: { max_tool_calls: 20, max_spend_usd: 2.0 },
  escalate: [{ when: 'mismatch_value_gbp > 10000', to: 'ap-duty-controller', timeout_seconds: 3600 }],
  on_no_response: 'deny',
};

validate(envelope); // throws ValidationError, naming the field

const point = new EnforcementPoint(envelope);
```

### Guard an existing agent

`guard` wraps the function your agent already calls tools through, so enforcement is
one line rather than a restructuring. It works on sync and async callers alike, and
keeps the wrapped function's own signature.

```ts
const guardedCallTool = point.guard(callTool);

try {
  await guardedCallTool('issue_payment', { invoice_id: '88413', amount_gbp: 24900 });
} catch (error) {
  if (error instanceof Refused) {
    console.log(error.decision.rule);   // 'tools.deny'
    console.log(error.decision.detail); // why, in words an operator can act on
  }
}
```

The tool is never reached. A decision made after the call has already run is a report,
not an enforcement point.

### Escalation is not refusal

`Escalated` is a separate error from `Refused` on purpose. Collapsing the two turns "a
named person must decide this" into "no", which loses the reason for having an
escalation path at all.

```ts
import { Escalated } from 'intent-envelope';

try {
  await guardedCallTool('send_email', { template: 'mismatch_summary', to: 'ap-team@example.com' });
} catch (error) {
  if (error instanceof Escalated) {
    error.decision.escalateTo;     // 'ap-duty-controller'
    error.decision.timeoutSeconds; // 3600
  }
}
```

If nobody answers within the timeout, `on_no_response` decides. Setting it to `deny`
means an unanswered escalation fails closed.

### Decide without enforcing

`check` records a decision and returns it instead of throwing, which is what you want
when shadowing an envelope against live traffic before you turn it on.

```ts
const decision = point.check('send_email', { template: 'mismatch_summary', to: 'elsewhere@example.com' });
decision.result; // 'deny'
decision.rule;   // 'recipients'
```

### The ledger

Every decision is recorded, including the refusals. A log holding only what succeeded
cannot answer the question an incident asks, which is what the agent tried to do.

```ts
point.ledger();  // one record per decision, in order, as section 5 of the spec requires
point.summary(); // { allow: 3, deny: 2, escalate: 1 }
```

Each record names the envelope, its revision, the agent identity, the tool, the result,
the rule that decided and when. That is enough to reconstruct a run months later,
against the exact envelope revision that was in force at the time.

## What it does not do

Worth being explicit, because a guardrail people misunderstand is worse than none.

- It decides tool calls. It does not inspect prompts or model output, and it will not
  notice an agent being talked into something as long as the resulting calls stay
  inside the envelope.
- It enforces where it sits. Calls that bypass the enforcement point are not governed by
  it, so the envelope is only as good as the chokepoint you put it in.
- The default condition matcher handles the simple numeric comparisons in `escalate.when`
  and raises `UnsupportedCondition` on anything else, rather than guessing. Pass your own
  matcher for richer expressions. Guessing wrong here means failing open.
- `limits.max_runtime_seconds` is enforced only if you tell the enforcement point how
  much time has passed, since this package does not own your run loop.

## The same decisions in Python

There is a [Python implementation](../python) in this repository. Both run the same
language-neutral case files in [`conformance/decisions`](../../conformance/decisions),
and `node tools/cross-check.mjs` at the repository root runs the two over every case and
diffs the answers. Each package passing its own suite proves only that it agrees with
itself; that script proves the two agree with each other, which is what the
specification actually claims: an envelope means the same thing whichever enforcement
point reads it.

## Development

```sh
npm test            # the conformance cases and the enforcement suite
npm run typecheck   # types, including the tests
npm run smoke       # pack, install the tarball, make a decision with the installed copy
npm run build       # emit dist/
npm run gen:schema  # regenerate src/schema.ts from schema/intent-envelope-0.1.json
```

`npm run smoke` exists because the test suite runs against this source tree, where Node
strips the types out of a `.ts` file quite happily. It cannot see the failure that
matters at publish time: Node refuses to strip types under `node_modules`, so a package
pointing at its own sources throws on a consumer's first import. Forty passing tests say
nothing about that, because none of them import the package the way a consumer does.
